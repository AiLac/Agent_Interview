# 给 Agent 加 Google 搜索，选 MCP 还是 Skill？

如果从零给一个 Agent 加低频搜索，而且宿主已经能运行脚本、访问搜索 API，我会先选 **Skill + 搜索脚本**。如果要让几个不同的 Agent 宿主共同调用一项由团队维护的搜索服务，我会选 **MCP 工具**。这两种设计可以使用同一个搜索后端。选型取决于谁执行代码、谁维护接口，以及模型每次需要读多少信息。

## 从一次查询看两种方案

假设用户说：“帮我用 Google 搜一下 Java 虚拟线程，给我两条结果。”为便于比较，假定两种方案都有可用的 Google 搜索 API、相同的凭据与配额，都提交同一查询，返回标题、网址和摘要。下面是设计示例。

| 一次查询经过的步骤 | Skill + 搜索脚本 | MCP 工具 |
| --- | --- | --- |
| 宿主怎样发现能力？ | 宿主先提供 Skill 的名称和简介。任务匹配时，Agent 读取 `SKILL.md`，得知如何运行脚本 | 宿主中的 MCP 客户端连接已配置的服务，初始化后通过 `tools/list` 取得工具名、说明和 `inputSchema`（输入参数的结构与约束） |
| 谁发起动作？ | Agent 按说明，请宿主的执行工具用搜索词和条数运行脚本 | 模型选中 `google_search` 并给出参数，宿主通过 MCP 客户端发送 `tools/call` |
| 谁访问 Google？ | 脚本读取运行环境提供的凭据并请求搜索 API | MCP 服务端的工具处理函数读取其运行环境提供的凭据并请求同一 API |
| 结果怎样回来？ | 脚本可以输出 JSON，由执行工具把结果交给 Agent | 服务端通过 MCP 返回工具结果，宿主将结果交给模型 |

**MCP（Model Context Protocol）约定了客户端和服务端如何交换消息。Skill 把完成任务的说明、可选脚本和参考材料放在一起，供 Agent 按需使用。** 熟悉 Java 的话，可以把底层搜索想象成一个 `search(query, limit)` 方法。它既可以从命令行入口调用，也可以由 MCP 服务端调用。搜索数据来自哪里，取决于这个方法的实现。[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) · [Agent Skills 工作原理](https://agentskills.io/what-are-skills)

## Skill 按需加载，为什么还会选 MCP？

先看一个完全用不到搜索的请求：“解释 Java 静态内部类单例。”如果 Skill 只给模型看名称和一句简介，而宿主每轮都把所有 MCP 工具的完整参数说明交给模型，那么搜索 Skill 在这轮通常占用更少上下文。这就是**渐进式披露**的收益。模型先了解适用场景，任务匹配时才读取操作说明和所需材料。[Agent Skills 规范](https://agentskills.io/specification)

但还要区分两件事。**宿主拿到工具定义，就已经知道服务端有哪些工具。宿主和模型平台还可以决定在哪一轮把完整定义交给模型。** 客户端可以先保存 `tools/list` 的结果，等任务涉及搜索时才向模型提供对应定义。Claude API 的 Tool Search 是一个具体例子，配置为延迟加载的工具会在模型检索到它时进入上下文。`defer_loading` 属于该平台的机制，其他宿主需要分别确认。[Claude Tool Search 文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)

| 模型当前要做什么？ | 采用渐进式披露的 Skill | 全量加载的 MCP 工具 | 按需加载的 MCP 工具 |
| --- | --- | --- | --- |
| 本轮用不到搜索 | 通常只看到名称和简介 | 搜索工具的描述和参数结构已经进入上下文 | 发现机制本身可能占用上下文，完整搜索工具定义可推迟加载 |
| 首次需要搜索 | 读取操作说明，再请求宿主运行脚本。脚本源码通常无需读入 | 工具已可见，可以直接给出调用参数 | 先发现或选中工具，再使用加载的定义发起调用 |
| 搜索结果很长 | 可以在脚本里截取需要的字段 | 可以在服务端或宿主里裁剪结果 | 同样可以裁剪。延迟加载主要影响工具定义 |

所以比较成本时，可以让两种方案都回答一个常识问题，再完成一个必须联网的查询。使用同一模型、相同查询和结果长度，分别记录每轮输入 token、完成查询所需的模型轮次以及端到端耗时。如果低频能力很多，观察闲置时的成本更有意义。如果每次请求都要搜索，首次发现工具或读取说明的步骤就更值得关注。

## 哪些需求会改变选型？

| 需求或约束 | 更合适的做法 | 选择理由 |
| --- | --- | --- |
| 单个 Agent 偶尔搜索，宿主具备脚本运行环境、网络和凭据 | Skill + 脚本 | 写好查询入口和用法即可交付，也容易在本机用相同参数复现 |
| 多个支持 MCP 的宿主需要共用搜索服务，运行环境各异 | 远程 MCP 服务 | 每个宿主可以按同一接口发现和调用工具。搜索实现可以统一更新，各端无需安装脚本依赖 |
| 宿主只允许调用指定工具，Google 凭据由独立服务持有 | 在独立服务中执行查询，通过宿主支持的 MCP 接口暴露 | 宿主只需发送查询参数。独立部署和服务端实现负责凭据隔离、鉴权与配额，选用 MCP 本身不会自动提供这些能力 |
| 已有搜索入口，现在要统一资料核实方法 | 在已有工具之上添加 Skill | 可以复用一套查询改写、来源选择和证据核对方法，底层继续使用原搜索工具 |

例如，用户把任务改成“核实某个 JDK 版本里的虚拟线程是预览还是正式特性，并给出处”。这时搜索只完成了第一步。Skill 可以指导 Agent 确认目标版本、优先查找 OpenJDK 的 JEP、使用网页读取工具打开原文、核对交付版本，再引用证据回答。若搜索能力已由 MCP 提供，这个 Skill 可以直接调用它。

## 用仓库里的 Java demo 校验理解

查看示例的运行记录，教学客户端用 `query="Java 虚拟线程"`、`limit=2` 调用 `google_search`。调用成功，`mock=true`，`totalMatches=3`，最终返回两条。客户端按代码选定工具，服务端调用 `MockSearch.search()`，数据来自六条固定的内存语料。这份记录验证了两个 Java 进程间的工具发现与调用，真实 Google 接入以及模型自主选择工具需要分别验证。[客户端运行记录](../mcp%20demo实践/verification/demo-client.stdout.txt) · [搜索实现](../mcp%20demo实践/src/demo/MockSearch.java)

这也解释了两种建议各自的前提。沿用 demo 时，已有可复用的 MCP 接口，接入真实搜索可以保留 `google_search(query, limit)`，替换后端并更新模拟标记和说明。从零实现时，这部分复用收益尚不存在。若只有一个可执行脚本的宿主，Skill 已足以交付查询。当多个调用方确实需要共享服务，MCP 的标准调用接口才产生可比较的工程收益。

## 面试时怎样回答

> 我会先明确搜索由谁执行、哪些宿主要复用它。单个 Agent 低频使用，而且已有脚本和联网权限时，我倾向于 Skill 加脚本。多个宿主需要共享一个独立维护的搜索服务时，我倾向于 MCP。我会检查宿主对上下文的处理，因为 Skill 能按需读取，MCP 工具定义也可以延迟加载。如果任务还包括核对版本、读取原文和引用证据，我会把这套方法写成 Skill，复用底层搜索工具。
